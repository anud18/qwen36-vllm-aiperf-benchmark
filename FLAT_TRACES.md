# Flat traces — flattened multi-turn workloads with machine-independent input tokens

How to build, run, and inspect the `*_flat` datasets used in the NVFP4 cross-hardware
sweep. Results and analysis live in [RESULTS_nvfp4.md](RESULTS_nvfp4.md) (flat-trace
sections); this file is the usage guide.

## Why they exist

The multi-turn workloads (chatbot/agent/coding) have *emergent* ISL: which sessions reach
which turn depth inside the request budget depends on concurrency and machine speed, so two
machines never measure the same input tokens (e.g. coding r1.0: Spark ISL 13.9k vs 5090's
21.8k — the slow machine degenerates to mostly first turns). The flat variants remove that
confound by pre-flattening every conversation turn into one **independent** request whose
full history is fixed in the file — any machine serving the same model/template receives
bit-identical input tokens.

**Verified**: full sweep run twice on the H100 (`results/nvfp4/h100/*_flat` vs
`results/nvfp4/h100run2/`) — 9 points × 96 requests, per-request ISL bit-identical,
prefix-cache queries reproduce exactly.

## Files & format (v2, original text)

`datasets/aiperf/nvfp4_{chatbot,agent,coding}_flat.jsonl` — 384 entries each, aiperf
`mooncake_trace` **`messages` mode**. Entry k of a session carries the real conversation
history verbatim and always ends on a user turn:

```json
{"messages": [{"role":"user","content":"..."},
              {"role":"assistant","content":"..."},
              {"role":"user","content":"..."}],
 "output_length": 329,
 "extra": {"chat_template_kwargs": {"enable_thinking": false}}}
```

Entries are ordered session-by-session, turn-by-turn, so every sweep point consumes the
same first `warmup + request-count` entries in the same order.

Assistant-reply sources:

- **chatbot** — ShareGPT's own gpt replies (true original text); sessions matched back to
  their ShareGPT entries by exact user-text sequence, `output_length` keeps the payload's
  `max_completion_tokens` (aiperf derives it from the same reply).
- **agent / coding** — the datasets carry no assistant text, so replies were generated once
  (greedy: temperature 0, seed 42, thinking off) and frozen; raw generations live in
  `datasets/aiperf/canonical/*_replies.jsonl`.
- **toolagent** needs no flat variant — it is already a lengths-declared trace.
  **rag** needs none either: `single_turn`, one independent real-text request per entry.

Current build (2026-07-28): **384 entries**, `--osl-cap 2048`, canonical replies generated by
**GLM-5.2** on the NCHC gateway. 384 = warmup 16 + `REQS` 320, the largest sweep point.

| file | entries | sessions | max turns | ISL avg/min/max (server tokens) | OSL avg/max |
|---|--:|--:|--:|---|--:|
| `nvfp4_chatbot_flat.jsonl` | 384 | 109 | 11 | 600 / 10 / 2,003 | 250 / 870 |
| `nvfp4_agent_flat.jsonl` | 384 | 88 | 6 | 3,004 / 379 / 12,288 | 256 / 1,381 |
| `nvfp4_coding_flat.jsonl` | 384 | 64 | 6 | 29,894 / 12,487 / 84,401 | 584 / 2,048 |

ISL is measured server-side (one `max_completion_tokens=1` request per entry → `prompt_tokens`).
The 2048 cap clips **93/384** coding turns (agent and chatbot never reach it). A cap-8192
build of the same sessions is kept in `datasets/aiperf/archive_glm52_osl8192/` for reference —
there coding OSL avg rises 584 → 1,693 and, because longer replies feed back into the history
of later turns in the same session, ISL rises with it (avg 33,195, max 115,687).

Other builds kept: `datasets/aiperf/archive_qwen36/` (Qwen3.6 replies, 240 entries, cap 2048 —
the dataset the spark/5090/h100 flat results were measured against). Different entry counts ⇒
a sweep point consumes a different slice of sessions, so numbers across builds are **not
comparable**.

## Rebuild

```bash
# chatbot: no server needed (ShareGPT cache at .cache/aiperf/datasets/ + a materialized
# inputs.json from any past chatbot run for session order)
python3 scripts/build_flat_text_traces.py chatbot --n-entries 384 --osl-cap 2048

# agent/coding: needs an endpoint for the one-time canonical generation
# (cached in datasets/aiperf/canonical/ — reruns only generate MISSING sessions, so
#  changing --osl-cap means deleting the cache first, otherwise clipped replies survive)
API_KEY=... python3 scripts/build_flat_text_traces.py agent coding \
  --n-entries 384 --osl-cap 2048 --model GLM-5.2 \
  --url https://inner-medusa.genai.nchc.org.tw
```

`--n-entries` must be ≥ `warmup + request-count` of the largest sweep point, or aiperf wraps
around and replays early entries (inflating prefix-cache hits). `--osl-cap` sets both the
`max_tokens` used for canonical generation and the ceiling written into `output_length`.

## Run

Same driver as every other workload — the flat cases are wired into `run_nvfp4.sh`:

```bash
# local box (spark/5090)
NODE=spark POINTS="c2 c8 c32" bash scripts/run_nvfp4.sh chatbot_flat agent_flat coding_flat

# shared box (H100 example: container-name prefixes + user-dir HF cache)
NODE=h100 VLLM_CNAME=an-hao-vllm-nvfp4 CPREFIX=an-hao-aiperf HF_DIR=$HOME/900g/an-hao/hf \
  POINTS="c2 c8 c32" bash scripts/run_nvfp4.sh chatbot_flat agent_flat coding_flat

# managed endpoint we do not own (NCHC GLM-5.2 gateway)
API_KEY=... REMOTE=1 NODE=glm52 REQS=320 SERVED_NAME=GLM-5.2 \
  URL=https://inner-medusa.genai.nchc.org.tw TOKENIZER=zai-org/GLM-5.2-FP8 \
  OUTBASE=results/nvfp4/glm52 POINTS="c2 c8 c32" \
  bash scripts/run_nvfp4.sh chatbot_flat agent_flat coding_flat rag toolagent
```

`REMOTE=1` exists because the gateway only serves `/v1/*` — `/metrics`, `/health` and
`/reset_prefix_cache` all 403. It skips the server restart and the per-point prefix-cache
reset, drops the engine-wedge watchdog to a plain tlimit backstop, writes
`prefix.json` as `{"unavailable":true}`, and passes `API_KEY` to aiperf as `--api-key`.
The gateway also 429s under sustained bursts (it rejected 384 consecutive large-prompt
requests at 6-way concurrency, then served the same load fine a minute later); aiperf
records 429s as request errors rather than retrying, so check the error count per point.

Two things the messages mode requires (both already wired in):

- aiperf **cannot client-side-tokenize raw messages** → the runner passes
  `--use-server-token-count`, so ISL = server-reported `usage.prompt_tokens`
  (includes chat-template tokens — slightly above client-side text counts).
- The server must return usage on streaming responses; aiperf configures
  `stream_options` itself when server token counts are enabled (entries may also carry
  `extra.stream_options.include_usage` — redundant but harmless).

**OSL is pinned too** (built with `--force-osl`, 2026-07-28): every entry carries
`"ignore_eos": true`, so against a vLLM you control the measured OSL equals `output_length`
exactly — verified end-to-end through aiperf on a local `v0.24.0` server, 16-32 requests per
workload, measured avg/min/max identical to declared (chatbot 279.5/54/641, agent
195.6/80/452, coding 39.9/13/156). Both sides of the trace are then machine-independent.
Two consequences: the OSL cap now decides real decode work (the 93 clipped coding turns each
generate a full 2,048 tokens, so coding is heavier than a natural-EOS run), and `ignore_eos`
must sit at the **top level** of the request body — aiperf's in-data `extra` is merged there,
but a nested `extra_body: {ignore_eos: ...}` is ignored by the server.

OSL **cannot** be pinned on the NCHC gateway, only capped — the same dataset still runs there,
the parameter is just dropped, so those results are not comparable with self-hosted ones.
`output_length` is sent as
`max_completion_tokens`, and the vLLM extensions that would force an exact length —
`ignore_eos`, `min_tokens`, `min_completion_tokens` — are all silently dropped by the
LiteLLM layer (a cap-200 request still stops at 12 tokens; no error either way). Greedy
(`temperature 0`, `seed 42`, written into every entry's `extra`) removes sampling noise but
does not reproduce the canonical lengths on multi-turn contexts — replaying agent entries
gave 332→214, 180→168, 188→171, because batch composition on a shared server moves the EOS
point. Against a vLLM you control, `ignore_eos: true` does work. Note that chatbot entries
appear to "match" exactly: their cap comes from ShareGPT's human replies, which GLM-5.2
overruns every time, so they finish with `finish_reason=length` — truncation, not agreement.

Generation stays live, so the output side is expected to move; the input side is what
the flat variants fix.

## Preview

Up to 5 entries per dataset, up to 1000 chars per entry:

```bash
python3 - <<'EOF' | less
import json
for f in ["datasets/aiperf/nvfp4_chatbot_flat.jsonl",
          "datasets/aiperf/nvfp4_agent_flat.jsonl",
          "datasets/aiperf/nvfp4_coding_flat.jsonl"]:
    print("\n" + "=" * 30, f, "=" * 30)
    for i, line in enumerate(open(f)):
        if i >= 5:                         # up to 5 entries per dataset
            break
        d = json.loads(line)
        print(f"\n--- entry {i} | {len(d['messages'])} msgs | output_length={d['output_length']}")
        budget = 1000                      # up to 1000 chars per entry
        for m in d["messages"]:
            if budget <= 0:
                print("      …(entry truncated at 1000 chars)")
                break
            c = m["content"].replace("\n", "\\n")
            shown = c[:budget]
            more = f" …[+{len(c)-len(shown)} chars]" if len(c) > len(shown) else ""
            print(f"  [{m['role']:>9}] {shown}{more}")
            budget -= len(shown)
EOF
```

## v1 (synthetic) note

The first flat generation (`scripts/build_flat_traces.py`) declared token *lengths* +
`hash_ids` and let aiperf synthesize prompt text. The Spark/5090 flat results under
`results/nvfp4/{spark,5090}/*_flat` predate v2 and were measured against those synthetic
files — regenerate with that script if you ever need the synthetic form back. v2 (this
guide) supersedes it: real text also restores realistic prefix sharing that the 512-token
hash blocks understated for chat (chatbot hit-rate 1.5% → ~22–26%).
